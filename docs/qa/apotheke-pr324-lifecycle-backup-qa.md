## Prior findings

- **L-2167 closed** (from #314: "once the backup endpoint is wired, every delete would fail and no purge could ever run … Fix it in the backup endpoint PR: export before the status change, or a backup-only start"). A backup-only start now lets the delete and suspended exports reach the app. End to end it still fails as `backup_404` until #318 sets `APOTHEKE_HOSTED`. That fails closed, and it's a stated risk.

## New findings

- **L-2230:** a failed export leaves the container running. When the backup step fails (any `LifecycleError`, or retries exhausted), `runJob` fails the job without running `export.stop` or `delete.export.stop`. A suspended or deleting installation's container that `opsBackup` started then runs until the inactivity timeout (15 min by default), and also between retries. Probe: a 404 answer leaves `running` true. Until #318 lands, every export or delete of a stopped installation fails this way. Public requests stay gated (`opsOnly`), except as in L-2231. Fix: a best-effort stop (unless active) in the failure path, or stop the container in `opsBackup` when it started it and got no key.
- **L-2231:** `opsOnly` lives only in memory. A fresh object over a running container sets `ready = true` and `opsOnly = false`, so public requests skip `publicStart`. Probe: suspended and deleting both give 200 to a public request. After a DO reset during or after a backup start, routing covers this with 402 (suspended) and 410 (deleting) once each isolate's 30 s route cache expires, since `routeCache.purge` is a no-op. `delete.export` starts the container seconds after `delete.status`, inside that window, and L-2230 lengthens the container's life. Both a reset and a stale isolate are needed, so this is Low. Fix: in the constructor, set `opsOnly = true` for a running non-primary container (one D1 read on the next public request), or keep the flag in storage.
- **N-2232:** `opsOnly` is set only when the container is not running. A running but not-ready container (`ready` false) passes the start gate with `opsStart`, and public requests then reach a suspended installation (probe: 200). No production path was found, because suspend and delete stop first and an earlier ops start already set the flag. Set `opsOnly` whenever `opsBackup` starts through the gate.
- **N-2233:** `key.startsWith(installationPrefix(doName))` is always true, because the key is built from that prefix (M08), so `rel` is the only guard. `rel` accepts `%2e%2e`, U+2025, full-width dots, spaces and newlines. These are literal R2 keys with no escape today, but E6's download link must encode each part and never decode it. A tighter check would be `^backups/[A-Za-z0-9_-]+/manifest\.json$`, the PHP contract. Prefixes end in `/`, so `inst1` vs `inst10` is safe.
- **N-2234:** every throw from `opsBackup` is retried as `backup_unreachable`, permanent ones included: a refused start (no routes, or status `deleted`), primary (unreachable after `target()`), and a bad APP_KEY. That means up to 10 × 3 min, plus a 90 s start wait each, before the job fails. It fails closed but slowly, and it hides the cause. A claim left by a dead PHP request (taken over after 2 h) uses up the 409 retries, and the job fails as `backup_409`.
- **N-2235:** test gaps M03, M05 and M10 (an array key, `backups/x/`, a 204 or 302 answer). One prose line in operator-console.md ("…fails as `backup_404`. Routes are cached…") is 146 characters long, not wrapped at 120.
- Stated risks accepted: `backup_404` until #318; a 500 retried 10 times at up to 900 s each; no fetch timeout beyond the step timeout; limits off, so start-time writes aren't counted; and new step names (no instance deployed). The eviction risk is L-2231.
