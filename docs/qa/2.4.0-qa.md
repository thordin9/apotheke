# QA: Apotheke 2.4.0 (Feature 8: AI autofill on demand)

PR #25 (`feat/autofill-on-demand-v2`, head `d3fff93`; replaces #24, same code). QA run on 2026-10-18 and finished on 2026-10-19 (EEST), the head unchanged,
against the autofill stub (`php -S 127.0.0.1:8090 tests/stubs/autofill-stub.php`) only. No real service or
Jetson was used. Every scenario ran on a fresh, empty `DATA_DIR`.

## 3. Findings

| ID | Severity | Finding | Repro |
|----|----------|---------|-------|
| L1 | Low–Medium (a11y) | Keyboard focus is lost when Analyze is pressed. The button disables while it runs, focus falls to `<body>` and stays there after it re-enables, so keyboard and screen-reader users have to tab back from the top. | Item form, pick a photo, Tab to *Analyze photo*, press Enter; `document.activeElement` is BODY during and after the run. Fix idea: keep the button focusable (`aria-disabled` instead of `disabled`), or restore focus when it finishes. |
| L2 | Low (UX/docs) | *Test with a photo* on a cold model fails straight away with *the model is warming up. Try again in 3 s* and does not retry, whereas the item form retries once (A1). The admin guide says the test "can take as long as the timeout, e.g. on the first photo after a model switch". | Stub `/m/switch/n/…`, choose the second model, press *Test with a photo*: it fails at once, and a second click succeeds. Fix: apply the A1 single retry to the test as well, or reword the guide. |
| L3 | Low | Nothing in the browser checks the 10 MiB limit. A photo that is still too large after resizing (e.g. noisy PNG on a 4096 px profile) is uploaded in full (23 MB here) before the server rejects it, and the message *the photo is too large* does not state the limit. | Profile `/z/4096`, pick `noise_rgba_2400.png`, Analyze. |
| L4 | Info (resolved: as intended) | `ready` from `/v1/info` does not gate the Analyze button. That deviates from the original spec line "`ready` only enables the button", but it matches PM's later requirement that `loaded`/`ready` must not be treated as warm (P2). A cold model is handled by the bar/hint and the warming-up retry. | Code review of `app.js` and `autofill.php`. Keep it this way; reword the spec line. |
| L5 | Low (docs) | The admin guide reads *loaded* as "in memory right now" and says that switching to a model that is not loaded makes the next photo slow. This implies that a *loaded* model answers fast, which PM's requirement rules out: on the Jetson, `loaded` turns true early during a cold load. The code is right (P2); only the wording is off. | `docs/autofill-admin-guide.md` (Model bullet), `docs/autofill.md` (Model row). Suggested: "*loaded* is what the service reports; Apotheke does not rely on it, and any photo can still be a cold start, so the progress bar and its hint always allow for the full timeout." |
| I1 | Info | The model dropdown shows "· loaded". It is cosmetic and not used for the estimate or the hint (see L5 for the wording). | `settings_v12_*` |
| I2 | Info | When no size is flagged `recommended`, Apotheke picks the largest size ≤ 1024 (e.g. 800 out of 448/800/1600) and labels it *Recommended*. That is reasonable, but the service does not call it recommended. | `/z/448,800,1600` |
| I3 | Info | A stored size the service no longer offers is still sent, labelled "(not offered by the service)". Acceptable; the admin sees the label. | |
| I4 | Info | After a cancelled analysis the hidden progress element keeps old percentage text. Not visible. | |
