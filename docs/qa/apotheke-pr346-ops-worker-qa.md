## Findings

- **N-2400:** a failed certs fetch isn't throttled or cached. After 30 s, every request with an unknown `kid` fetches again (5 requests gave 5 fetches) and gets 503 instead of 401, and the fetch has no timeout. Cached keys keep working. Access sits in front and sets the header, so outside requests can't reach this. Optional: keep the failure time and apply the 30 s throttle to it too.
- **N-2401:** `readBody` reads the whole body before its 4 KiB check when there is no `Content-Length`, and the body is checked before `primary` and the lookup. So `primary` with a bad body gives 422, not 403, while the docs list the body check last. The platform caps the body size, and the caller has already passed Access and CSRF. Optional: say in the docs that the body is checked first, and mention the 60 s `nbf`/`iat` skew.
- **N-2402:** two guards have no test, and the mutants that drop them are equivalent. Without the `OPTIONS` 405, a request with a token still gets 405, and one without a token gets 401. Without the `do_name === primary` row check, `do_name` is `UNIQUE` and the seed takes `primary`, and `Ops` refuses it again.
- Stated risks accepted: a reset whose audit write fails is done but unaudited (503 `audit_failed`). A claim token whose audit fails is created but never delivered, and the next claim voids it. Refusals aren't audited. Replay within the signature window stays open until Coder2's PR (L-2350). There is no Workflow binding yet. The D1 id, the host, the Access application and the deploy are set up outside the repo. The console has no claim or reset calls yet (F1b).
